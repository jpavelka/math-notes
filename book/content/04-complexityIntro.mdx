## Running times {/* sec:runningTimes */}

What we'd really like to nail down first is how to describe the running time of certain algorithms. More specifically, we'd like to know how the running time changes as the size of the problem increases. This "size" we're discussing has something to do with the number of items under consideration, for example the number of vertices and edges in the underlying graph in the case of <Ref id="prob:tsp"/> or <Ref id="prob:mst"/>.

### Input length {/* sec:inputLength */}

To make things a little more precise, let's suppose we have some given problem (say <Ref id="prob:tsp"/>) and let $X$ be an instance of that problem (i.e. a specific graph and set of edge costs). We'll define the _length_ of $X$ as follows:

<Definition id="def:length" title="Length">
For a given instance $X$ of an optimization or decision problem, the length of $X$ (denoted $L(X)$) is the number of characters required in a "standard" binary representation of the instance data. Informally, think of it as the disk space required to save the instance data on your computer.
</Definition>

Yes, that is a rather vague definition, and those scare quotes around the word "standard" are doing a lot of lifting. Like I said, we're not being completely formal here. For our purposes, it suffices to think of $L(X)$ as the size of a file holding the instance data on your computer.

But just in case, let's see an example of what this might mean. Consider an instance of <Ref id="prob:knapsack"/> with item weights and values defined in <Ref id="tab:knapsackExampleTable"/> and an overall weight limit of 7.

<Table id="tab:knapsackExampleTable">
| Item | Weight | Value |
|------|--------|-------|
| 1    | 2      | 10    |
| 2    | 1      | 7     |
| 3    | 6      | 25    |
| 4    | 5      | 24    |
</Table>

How would we represent this instance in binary? First, we need to identify the relevant instance data, which for knapsack is the item weights and values. We could imagine the items having names, but that's not really important for solving the instance, so that can be ignored. So we just need the weights and values, making sure that these values for each respective item are linked in some manner. For convenience, let's allow ourselves spaces and newline characters in addition to the binary 1s and 0s. Then we might represent this instance as:

<Figure id="fig:knapsackExampleInstanceRepresentation" caption={<>A binary representation of the <Ref id="prob:knapsack"/> instance with item weights/values from <Ref id="tab:knapsackExampleTable"/> and a weight limit of 7.</>}>
$$
\begin{align*}
&10\ 1010\\
&1\ 111\\
&110\ 11001\\
&101\ 11000\\
&111
\end{align*}
$$
</Figure>

Each row except the last has two numbers: the binary representation of each item's weight and value, respectively. The space character separates the weight number from the value number, and new lines separate data for different items. On the last line, we have the binary representation of the weight limit $b$. In all, there are 37 total "0", "1", space, and newline characters in the representation, so under this representation the length of the instance is 37.

Figuring out the length for any given instance isn't so bad, but what will be most useful to us is knowing roughly how $L(X)$ grows as the relevant inputs to $X$ change. In the case of <Ref id="prob:knapsack"/>, the relevant input is the size of the set of items $J$, as well as the numbers that make up the weight limit and the item weights and values. I think the relationship with $|J|$ is pretty clear: we add a new row to the representation for every item added to the instance, so the length scales linearly (roughly 1:1) with $|J|$.

What about the weights and values? They affect the size too, but it's not really in proportion to the numeric values, is it? The largest number represented in <Ref id="fig:knapsackExampleInstanceRepresentation"/> is 25, but we don't need 25 bits to write down that number. Since 25 written in binary is 11001, we only need 5 bits to describe it. More generally, for some integer $n$, we only need $\ceil{\log_2(n)}$ bits to represent it. For convenience, let's have $C$ equal to the maximum of all the $v_j$ and $w_j$ values in the instance, as well as the weight limit $b$. Since all but one row of the representation requires one weight and one value, and we have one of these rows per item in $|J|$, we can say that the size of an instance of <Ref id="prob:knapsack"/> is roughly $|J|(2\log_2(C))$ plus the contribution from the final weight limit row, giving a total of

$$
|J|(2\log_2(C)) + \log_2(C)
$$

You might complain that we're being a little sloppy, by rounding rows of the input up to the worst case $2\log_2(C)$. But compared to the conventions of the theory, we're actually being too precise! We're generally interested in worst-case scenarios, and even then not on the specifics of the numbers, but the way they grow as inputs grow. Put another way, we're more interested in shapes than exact magnitudes. So that $2\log_2(C)$ term can lose the "2" in front, since that doesn't affect the shape. Indeed, we don't care about the base of the logarithm either, since one of the properties of logs is that for any two bases $a,b>0$ (and $a,b\neq1$) we have:

$$
\log_b(x)=\log_a(x)\frac{1}{\log_a(b)}
$$

In other words, for given $a,b$, the two logarithms are only off by a constant factor. Consequently, you'll generally see that $|J|(2\log_2(C)) + \log_2(C)$ simplified to $|J|\log(C)$.

This "don't sweat the small stuff" philosophy is codified in the so-called "big-O" notation. The formal definition is that for two functions $f,g$ over the same domain, we say $f(x)\in\O{g(x)}$ (in English, "$f(x)$ is big O of $g(x)$") if there exists some positive $M\in\R_{>0}$ and $x_0$ in the domain such that

$$
|f(x)|\leq M|g(x)|\qquad \forall\ x\geq x_0.
$$

Basically, this says that for big enough values of $x$, $g(x)$ is at most a constant away from $f(x)$. Colloquially, think of it as saying "$g$ grows as fast or faster than $f$." The formal definition is a little scary, but the real point is to give us a framework where we can abstract away the little details, and say things like "the length of an instance of <Ref id="prob:knapsack"/> grows like $|J|\log|C|$", but more succinctly: "For instances $X$ of <Ref id="prob:knapsack"/>, $L(X)\in\O{|J|\log|C|}$".

### Polynomial time {/* sec:polyTime */}

Now suppose you have some problem $P$ (something like <Ref id="prob:knapsack"/> or <Ref id="prob:tsp"/>) and an algorithm $A$ for solving the problem. For any instance $X$ of $P$, let $f_A(X)$ be the number of "elementary calculations" (again, not being precise here, but think things like addition, multiplication, comparison, etc.) required to run algorithm $A$ on instance $X$. We use these $f_A(X)$ values to define $f_A^*(l)$, the _running time_ of algorithm $A$ (as a function of input length $l$) by taking an upper bound of the run times $f_A(X)$ for all instances $X$ with length $L(X)=l$. That is<Footnote/>:

<FootnoteBody>
Technically the maximum here should be replaced with a supremum. As we said, we're not being completely rigorous here, and it shouldn't make a difference for the algorithms we discuss.
</FootnoteBody>

$$ {#eq:runningTime}
f_A^*(l)=\max_{X\in P}\left\{f_A(X):L(X)=l\right\}
$$

<Definition id="def:runningTime" title="Running Time">
The maximum number of "elementary calculations" (things like addition, multiplication, comparison) required to complete a given <Ref id="def:algorithm" textTransform='lowercase' useTitle/> on any instance of a given problem. See <Ref id="eq:runningTime"/>.
</Definition>

It's worth calling out the "$\max$" in the definition, meaning that this is necessarily a worst-case measure of difficulty. It's entirely possible that an algorithm runs in short time on almost all inputs, but if the time taken on some small subset of instances grows quickly, that's all that matters for the definition.

That was quite a few wonky definitions, but the payoff is that we now have a succinct way to describe how an algorithm's running time changes as the size of the problem increases. The holy grail of algorithm design is to create a so-called _polynomial_ (or _polynomial-time_) algorithm.

<Definition id="def:polyAlgo" title="Polynomial-time Algorithm" alt="Polynomial Algorithm">
An <Ref id="def:algorithm" textTransform='lowercase' useTitle/>  whose <Ref id="def:runningTime" textTransform='lowercase' useTitle/> is bounded by a polynomial in the <Ref id="def:length" textTransform='lowercase' useTitle/> of the input.
</Definition>

Mathematically, an algorithm $A$ is a polynomial-time algorithm if there exists some integer $p\in\Z_{>0}$ such that

$$
f_A^*(l)\in\O{l^p}
$$

Let's try to make this more concrete, yes? As luck would have it, we've already seen a few polynomial algorithms. One such example is <Ref id="algo:prim"/> for <Ref id="prob:mst"/>. To show this, let's first analyze the length of an instance $X$ of <Ref id="prob:mst"/>. Actually, we won't be quite as formal as the above definitions would imply. For our purposes, it is good enough to just determine the main elements of the input length, which we'll loosely define as the relevant parameters whose combination gives the input length. To describe the input for <Ref id="prob:mst"/>, we need to identify the vertices and edges, plus give costs $c_e$ for each $e\in\{i,j\}$. If we let $C=\max_{e\in E} c_e$, then we can safely bound the input length by something on the order of $|V| + |E|\log C$.

Now let's think about the algorithm. How many elementary operations might it take (in a worst case) to complete <Ref id="algo:prim"/>? In each pass through the main iteration, we add a new edge to the tree. This keeps going until the tree is a spanning tree, so $|V|-1$ iterations in the main loop. Each loop requires us to check the costs on each edge incident to $U$. While the size of $U$ changes, we know in every case that the number of edges we check can be no more than $|E|$. So that's $\O{|E|}$ checks of edge costs, over $|V|-1\in\O{|V|}$ iterations, or $\O{|V||E|}$ operations.

Do we need to keep counting operations? I'd say no. Yes, there is the initialization step, but those are just one-off operations. Whatever we do there won't add up to anything that's $\O{|V||E|}$, so the initialization won't affect things asymptotically. Remember, the beauty of using big-O notation is that we don't need to sweat the small stuff!

Now, we have the components of the input length $|V|,|E|,\log C$, and as well as an asymptotic bound on the run time $\O{|V||E|}$. In our slightly-less-than-formal world, all that's left is to check if $|V||E|$ can be written as some polynomial function of the inputs $|V|,|E|,\log C$. The answer to that is an obvious yes! So <Ref id="algo:prim"/> is a polynomial-time algorithm for <Ref id="prob:mst"/>.

It might seem like I was being pretty sloppy there, but we must remember two things: First, we're not being very rigorous in this section 😊. Second, this exercise is all about finding valid bounds, not so much about being precise. Sure, if you get sloppy enough with your bound on steps of the algorithm, you may not be able to prove polynomiality. But in practice, you'd need to get really sloppy to miss it!

## The classes $\P$ and $\NP$ {/* sec:pAndNp */}

Now that we have the notion of run time defined, we're ready to start breaking down problems into groups of "easy" and "difficult" problems. But we first need to reckon with an inconvenient fact: It turns out the theory we're building toward isn't really about optimization problems, but instead so-called "decision problems".

<Definition id="def:decisionProblem" title="Decision Problem">
A problem for which the answer is either YES or NO.
</Definition>

The problems we've seen so far (like, <Ref id="prob:ip"/>, <Ref id="prob:lp"/> and all the various <Ref id="prob:combOpt"/>s) are not "yes" or "no" questions. They are optimization problems, asking you to find the best answer out of a set of feasible solutions. Luckily, there is a natural way to convert any given optimization problem to a decision problem. A general optimization problem may be stated as finding

$$
\argmax_{x\in S}f(x)
$$

for an appropriately defined feasible set $S$ and objective function $f$. The "decision version" of this problem would be stated as:

$$
\text{Is there an element }x\in S\text{ such that }f(x)\geq k\text{?}
$$

for some number $k\in\R$. In this way, we can easily create a "decision version" of all the problems we've discussed so far in the class.

### Easy to solve {/* sec:easyToSolve */}

With that aside, we're ready to define our first class of decision problems, which we call $\P$.

<Definition id="def:classP" title="$\P$">
The class of <Ref id="def:decisionProblem" altLabel="decision problems"/> which can be solved by a <Ref id="def:polyAlgo" useTitle textTransform="lowercase"/>.
</Definition>

Colloquially, we like to think of $\P$ as the set of "easy" problems. You can take that at face value, but it's worth pondering for a moment why that is. Surely, for a problem instance of length $l$, an algorithm that runs in $\O{l}$ steps must be better than an algorithm that runs in $\O{l^2}$. And surely _that_ algorithm is better than an algorithm that takes $\O{l^{10}}$ or $\O{l^{100}}$! And yet we want to say that a problem whose best-known algorithm takes $\O{l^{100}}$ steps is as easy as a problem with an algorithm taking $\O{l}$ steps. Why?

I will give two reasons. The first reason is more technical in nature, revolving around the way computer scientists do these analyses. Generally, you must specify a model of computation before doing your analysis. Classically, this would be a [Turing machine](https://en.wikipedia.org/wiki/Turing_machine)<Footnote/>, but there are other ones you can choose, not all of which are precisely equivalent. But generally computation time in different models will differ only by a polynomial factor of the input length, making the class $\P$ robust against the choice of computational model. This is a nice theoretical advantage.<Footnote/>

<FootnoteBody>
It's worth mentioning that a Turing machine is not an actual physical machine or computer, but rather an abstract mathematical model of one.
</FootnoteBody>

<FootnoteBody>
This notion of equivalence up to polynomial factors is also why I'm not too worried about the relaxed nature of the presentation in the chapter. Sure, you could do the work to get the number of steps just right, but with "only" polynomial differences, you'll generally get the same complexity class anyway.
</FootnoteBody>

The second reason: practical experience tells us that problems with polynomial-time algorithms really do tend to be the most realistically solvable ones. Of course, the degree of the polynomial does have plenty of practical importance, and an algorithm with a true $\O{l^{100}}$ running time will not be useful for most inputs. But history has shown us that once a polynomial algorithm is found for a given problem, even if the exponent is large initially, most of the hard work has been done. It will generally take a comparatively small amount of research to bring that exponent down to a more reasonable range, and the problem becomes tractable even for large inputs.

Of the problems we've discussed so far, which ones belong to $\P$? We've already discussed (toward the end of <Ref id="sec:polyTime"/>) how <Ref id="algo:prim"/> is a polynomial-time algorithm for <Ref id="prob:mst"/>. We technically can't say that <Ref id="prob:mst"/> is in $\P$ because we've defined <Ref id="prob:mst"/> as an optimization problem. But remember that each optimization problem has a conveniently-defined decision version, where the inputs to the decision problem are the same as the inputs to the optimization problem, plus the addition of some constant $k\in\R$. Then instead of finding the optimal value of the objective function, your task is to decide if the problem has a solution with an objective _at least as good_ as $k$<Footnote/>.

<FootnoteBody>
Meaning "less than or equal to $k$" in the case of a minimization problem, and "greater than or equal to $k$" for maximization.
</FootnoteBody>

So, does the decision version of <Ref id="prob:mst"/> have a polynomial-time algorithm? Yes! The algorithm is to simply run <Ref id="algo:prim"/>, then do one extra check: is the optimal objective at least as good as $k$? This extra check adds nothing to the algorithm run time in asymptotic terms, so the decision algorithm is still polynomial. Thus the decision version of <Ref id="prob:mst"/> is indeed in $\P$.

What about the other algorithms we've discussed so far? <Ref id="algo:tsp2Approx"/> does run in polynomial time, but is only an approximation algorithm. It therefore is not guaranteed to solve <Ref id="prob:tsp"/> or its decision variant, so we can't get any information from that one.

<Ref id="algo:dijkstra"/> is an exact algorithm for <Ref id="prob:shortestPath"/>. Let's check if it runs in polynomial time with respect to input length. Similar to <Ref id="prob:mst"/>, the inputs are a graph and some edge weights, so the input length is a (no more than polynomial) function of $|V|,|E|,$ and $\log C$ (where $C=\max_{e\in E}\{c_e\}$). The main iteration of the algorithm requires at most $|V|$ loops. Inside the main iteration we require a check on all vertices ($\O{|V|}$ checks) and there is a nested loop inside the main iteration again looping through a subset of the vertices $\O{|V|}$. There is only a constant number of operations inside this nested loop, so the action in there does not matter for the asymptotic analysis.

So, recap: $\O{|V|}$ loops in the main iteration, each requiring $\O{|V|}$ operations. So we require $\O{|V|^2}$ operations total. This is clearly (asymptotically bounded by) a polynomial in the input length. So we can find the optimal value in a polynomial number of steps, then simply check how the output compares with $k$, proving the decision version of  <Ref id="prob:shortestPath"/> is in $\P$.

Lastly, let's check <Ref id="algo:knapsackDP"/>. As we discussed earlier (and gave an example in <Ref id="fig:knapsackExampleInstanceRepresentation"/>), the length of an instance of <Ref id="prob:knapsack"/> is on the order of $|J|\log C$, where $C$ is the maximum of the $v_j,w_j,$ and $b$ values. The main iteration of the algorithm includes an outer loop with $n=|J|$ iterations, then an inner loop with $b\in\O{C}$ iterations. The number of operations per loop is constant, so the total number of operations is $\O{|J|C}$.

Initially, that looks like a polynomial in the input size. But actually, it's not. $C$ is a factor in the number of operations, but $\log C$ is the factor in the input size. Recall that by the definition of logarithms, for any base $b$ we have:

$$
b^{\log_b(C)} = C
$$

i.e. $C$ is exponentially larger than $\log C$<Footnote/>. So we can't bound the runtime by a polynomial in the input, thus <Ref id="algo:knapsackDP"/> is _not_ a polynomial algorithm for <Ref id="prob:knapsack"/>. Of course that doesn't mean that <Ref id="prob:knapsack"/> isn't a member of $\P$; the fact that one particular algorithm isn't polynomial doesn't mean that no polynomial algorithms exist. As it stands, nobody has found a polynomial algorithm for <Ref id="prob:knapsack"/>, but also nobody has proven that no such algorithm can exist.

<FootnoteBody>
In this situation, where an algorithm is polynomial in the _magnitude_ of some input numbers instead of the encoding length, we say the algorithm is _pseudo-polynomial_.
</FootnoteBody>

### Easy to verify {/* sec:easyToCheck */}

While $\P$ is an important class, we don't yet know if all our various <Ref id="prob:combOpt"/>s belong in it. But there is a different complexity class where they all fit in, called $\NP$.

<Definition id="def:classNP" title="$\NP$">
The class of decision problems for which there is an algorithm that, for every instance $X$ where the answer is YES, there exists a certificate $c$ such that

1. The length of $c$ is bounded by a polynomial in $L(X)$.
2. The algorithm run on $(X,c)$ can verify that $X$ is a YES instance in polynomial time.
</Definition>

Basically, for any YES instance, there is a small extra bit of data (the certificate) such that, with access to it and the problem instance, you can show in polynomial time that the answer is YES. Colloquially, you can think of $\NP$ as the class of decision problems where a YES answer can be verified easily.

Note that we've said nothing about how the certificate was obtained. It doesn't matter if there is an efficient way to compute it. All that matters is that for any YES instance, such a certificate exists.

This definition is maybe a little tough to parse at first, but it's really not so bad once you see a few examples. To that end, let's take <Ref id="prob:maxWeightIndSet"/> as an example, and for the instance let's look back to the graph in <Ref id="fig:indSetEx"/>. Since we're considering decision problems, let's set $k=13$ so that the question we're answering is "is there an independent set in the graph with weight at least 13?"

We've already solved this instance and know the optimal independent set has weight 14, so we already know this is a YES instance. Is there a small certificate we could present someone such that they can quickly verify that? Well, yes. Just list off the vertices in that optimal independent set. This is a list of $\O{|V|}$ vertices, so it is small enough to be a valid certificate. Then the verification algorithm consists of just checking that none of the vertices are adjacent (should take $\O{|E|}$ operations) and then adding up the weights of the vertices ($\O{|V|}$). This generalizes: for any YES instance of <Ref id="prob:maxWeightIndSet"/> there exists a certificate<Footnote/> of length $\O{|V|}$ and an algorithm that runs in $\O{|E|}$ steps to verify the YES. Then the two conditions of the definition are met, verifying that <Ref id="prob:maxWeightIndSet"/> is in $\NP$.

<FootnoteBody>
I'll mention again: it only matters that this certificate exists. Being able to find it quickly (or at all!) is not a requirement.
</FootnoteBody>

 Let's think of a different question — do certificates and verifying algorithms exist for NO instances of <Ref id="prob:maxWeightIndSet"/>? Decision problems that fit in this category belong to a class called $\coNP$.

<Definition id="def:classCoNP" title="$\coNP$">
The class of decision problems defined analogously to <Ref id="def:classNP" useTitle/>, except it is the NO instances which are verifiable.
</Definition>

Might <Ref id="prob:maxWeightIndSet"/> be in $\coNP$ as well? Again, this hasn't been ruled out, but so far as we know, there is no quick way to verify a NO instance.

What about <Ref id="prob:mst"/> or <Ref id="prob:shortestPath"/>, which we've already shown to be in $\P$. Are they also in $\NP$? Trivially, yes. Since they are in $\P$, you already have a polynomial algorithm to tell if a YES instance is a YES instance... the same polynomial algorithm that solves the problem in the first place! No certificate needed! Due to the same reasoning, all problems in $\P$ are in $\NP$, which we can write as $\P\subseteq\NP$. And by similar reasoning, $\P\subseteq\coNP$ as well.

And the other <Ref id="prob:combOpt"/>s we've studied? All of them lie in $\NP$. The reasoning mirrors the reasoning for <Ref id="prob:maxWeightIndSet"/>: if the answer is yes, just present an optimal solution as the certificate. For each problem, checking the validity of the solution can be done in time bounded by polynomials in the input size.

### Does $\P=\NP$? {/* sec:pEqualNP */}

It's worth pausing for a moment to reflect on the current state of knowledge in complexity theory. We've presented $\P$ and $\NP$ as two different classes, and we've shown that $\P\subseteq\NP$. But is it possible that the opposite relation $\NP\subseteq\P$ also holds, such that they are actually the same thing?

If you think about it for a bit, it seems like an absurd suggestion. Colloquially, this is like asking "is verifying an answer just as easy as finding an answer in the first place?" Surely it must be easier to verify an answer after given the proof, than it is to find the proof all by yourself. But so far, at least in the language of $\P$ and $\NP$, nobody has been able to prove it.

And it hasn't been for lack of effort! This question has been on the forefront of computer scientists' minds since the 1970s. The stakes were raised in the year 2000 when the Clay Mathematics Institute included the $\P$ vs $\NP$ problem among its seven [Millennium Prize Problems](https://www.claymath.org/millennium-problems), a list of important unsolved problems in a wide array of mathematical fields. The institute will award $1 million to anyone who resolves a problem from the list<Footnote/>.

<FootnoteBody>
So far, only one of those seven problems (the [Poincaré conjecture](https://en.wikipedia.org/wiki/Poincar%C3%A9_conjecture)) has been solved. Interestingly, [the person who solved it](https://en.wikipedia.org/wiki/Grigori_Perelman) turned down the money.
</FootnoteBody>

And the implications go well beyond the cash prize. For instance, if $\P\neq\NP$ then we'd know for certain that scalable algorithms for exact solutions to certain <Ref id="prob:combOpt"/>s cannot exist, meaning perhaps more time should be devoted to heuristics and approximations. Meanwhile, if $\P=\NP$, then many of the algorithms we use today for cryptography (to, for example, keep your bank credentials safe while shopping online) are unsafe in principle and potentially vulnerable to attack.

People also like to get philosophical when discussing the implications of $\P=\NP$, making provocative claims like "there is no difference between someone who can appreciate art and an artist" or "anyone who can recognize good music is as talented as Mozart". There's truth in these statements as metaphors, but sometimes I find it hard to tell if these people actually mean them literally. As far as I'm concerned, these sweeping metaphysical claims don't follow from the theory.

## Completeness and reductions {/* sec:reductions */}

In this section, we'll show how different (and sometimes seemingly unrelated) problems can be united via the concept of reduction. To do so, I'll need to introduce you to one of the most important problems in complexity theory. But before we get there, we should talk a little bit about Boolean algebra.

<Definition id="def:booleanAlgebra">
A branch of mathematics dealing with variables whose values are either "true" (1) or "false" (0).
</Definition>

In Boolean algebra, we have three elementary operations, "and" (also known as conjunction, and denoted by $\land$), "or" (disjunction, $\lor$) and "not" (negation, $\neg$). For Boolean variables $x$ and $y$, they follow these simple conditions:

$$
\begin{align*}
    x\land y&=\begin{cases}
        1&\text{if }x=1\text{ and }y=1\\
        0&\text{otherwise}
    \end{cases} \\
    x\lor y&=\begin{cases}
        1&\text{if }x=1\text{ or }y=1\\
        0&\text{otherwise}
    \end{cases} \\
    \neg x&=\begin{cases}
        1&\text{if }x=0\\
        0&\text{if }x=1
    \end{cases}
\end{align*}
$$

The expressions $x\land y$ and $x\lor y$ from above are known as _Boolean formulas_:

<Definition id="def:booleanFormula" title="Boolean Formula">
An expression involving Boolean variables (true/false or 0/1 values) and Boolean operations ($\land$, $\lor$, and $\neg$).
</Definition>

<Definition id="def:satisfiable" title="Satisfiable">
In <Ref id="def:booleanAlgebra"/>, a <Ref id="def:booleanFormula"/> is said to be satisfiable if there is some assignment of 0s and 1s to the variables that makes the formula evaluate to 1.
</Definition>

As an example, consider the following Boolean formula:

$$
\begin{align*}
    \phi=(\neg x\land y)\lor(x\land \neg z)
\end{align*}
$$

The formula is satisfiable, as letting $x=0$ and $y=1$ (and then $z$ either 0 or 1) makes it evaluate to 1.

An important problem in computer science asks if a given formula is satisfiable:

<Problem id="prob:sat" title="Satisfiability" label="SAT">
<ProblemInstance>
A <Ref id="def:booleanFormula" altLabel="Boolean formula"/> $\phi$.
</ProblemInstance>
<ProblemQuestion>
Is $\phi$ <Ref id="def:satisfiable" useTitle textTransform="lowercase"/>? That is, is there an assignment of 0s and 1s to the variables such that $\phi$ evaluates to 1?
</ProblemQuestion>
</Problem>

It should be clear that <Ref id="prob:sat"/> is in $\NP$: the certificate for a YES instance is simply the satisfying variable assignments, which can be checked quickly by plugging the values into the formula.

### $\NP$-completeness {/* sec:npCompleteness */}

What's less clear is that <Ref id="prob:sat"/> has a special property that relates it to _all other_ problems in $\NP$. It is not the only problem with this property, but it was the first one for which it was proven. It turns out that if you take an instance of _any_ problem in $\NP$, you can, in polynomial time, convert that instance into an instance of <Ref id="prob:sat"/>. Moreover, the conversion ensures that the instance of the original problem is a YES instance if and only if the converted <Ref id="prob:sat"/> instance is a YES instance.

It's a neat trick for sure, but there is a deeper implication. Suppose you happened to find a polynomial-time algorithm for <Ref id="prob:sat"/>. You could then use that algorithm to solve _any other_ $\NP$ problem in polynomial time. How? Take the instance of the other problem, reduce it in polynomial time (using the algorithm referenced above) to an instance of <Ref id="prob:sat"/>, then use your new polynomial algorithm for <Ref id="prob:sat"/> to get the answer. The addition of two polynomials is still a polynomial, so the total run time of this scheme is also polynomial.

This means that, by virtue of your new algorithm for this one problem, you've now proven that any problem in $\NP$ has a polynomial-time algorithm. This means you've shown that $\P=\NP$! Congratulations on the $1 million and your newfound celebrity!

This process of taking an instance of one problem, and converting it to an instance of another problem, is important enough to have its own name.

<Definition id="def:reduction" title="Reduction">
The process of converting an instance of one problem into an instance of another, while maintaining the property that the input instance is a YES instance if and only if the output instance is a YES instance.
</Definition>

<Definition id="def:polynomialReduction" title="Polynomial Reduction">
A <Ref id="def:reduction" useTitle textTransform="lowercase"/> that runs in <Ref id="def:polyAlgo" altLabel="polynomial time"/>.
</Definition>

If a problem is in some complexity class and has the property that any problem in that class can be reduced to it in polynomial time, this problem is said to be "complete" for the class. This is meant to convey that the problem somehow embodies all the difficulty of problems in the class. In that way, you may think of the complete problems as the hardest problems in a given class. Since <Ref id="prob:sat"/> satisfies this for the class $\NP$, we say that <Ref id="prob:sat"/> is _$\NP$-complete_.

<Definition id="def:npComplete" title="$\NP$-Complete">
A problem in the class $\NP$ for which there exists a polynomial reduction from any problem in $\NP$ to it.
</Definition>

Unfortunately, [the original proof](https://en.wikipedia.org/wiki/Cook%E2%80%93Levin_theorem) of <Ref id="prob:sat"/>'s $\NP$-completeness is way outside the scope of this course. We would need to build up a more rigorous version of complexity theory, and even then the proof itself can get pretty lengthy. It takes up 6(!) pages in the excellent text <Cite id="sipser2012introduction"/><Footnote/>.

<FootnoteBody>
That text has also been my main inspiration for most of this section.
</FootnoteBody>

Luckily, once you have one complete problem for a class, it becomes much easier to add more. Why? The original complete problem needs a reduction scheme for _any_ problem in the class. But once you already have <Ref id="prob:sat"/> as an $\NP$-complete problem, for subsequent problems in $\NP$ it suffices to only show a reduction from <Ref id="prob:sat"/> to the new problem. This works because any given problem in $\NP$ can be converted to <Ref id="prob:sat"/> in polynomial time, and then your new reduction will take it from <Ref id="prob:sat"/> to the problem of interest.

And there is no limit to the length of the chain of reductions, since the sum of a finite number of polynomials will always be a polynomial. So that is how $\NP$-completeness proofs go these days: pick some problem in $\NP$ and create a reduction from some known $\NP$-complete problem to your new problem.

### An example reduction {/* sec:exampleReduction */}

There is now a fairly large [collection of problems](https://en.wikipedia.org/wiki/List_of_NP-complete_problems) that have been proven to be $\NP$-complete. One such problem is a variant of <Ref id="prob:sat"/> that is a little easier to work with. We'll define it soon, but it will be useful to define a few more terms from Boolean algebra.

In a Boolean expression, any variable or negated variable (e.g. $x$ or $\neg x$) is called a _literal_. A _clause_ is a sequence of literals connected with "or" operators, e.g. $x_1\lor\neg x_2\lor x_3$. A Boolean formula is said to be in _conjunctive normal form_ if it comprises several clauses connected with "and" operators.

<Definition id="def:literal" title="Literal">
A variable or negated variable in a Boolean formula. For example, in the formula

$$(x_1\lor x_2)\land(\neg x_3\lor \neg x_2),$$

$x_1$, $x_2$, $\neg x_2$, and $\neg x_3$ are all literals.
</Definition>

<Definition id="def:clause" title="Clause">
Several Boolean <Ref id="def:literal" altLabel='literals'/> connected with "or" operators, e.g. $x_1\lor\neg x_2\lor x_3$.
</Definition>

<Definition id="def:cnf" title="Conjunctive Normal Form">
A Boolean formula comprising several <Ref id="def:clause" altLabel='clauses'/> connected with "and" operators.
</Definition>

So the formula

$$
(x_1\lor x_2\lor \neg x_3)\land(x_4\lor\neg x_1\lor x_3)\land(\neg x_2\lor x_4\lor \neg x_1)
$$

is in conjunctive normal form.

We're now ready to define our more user-friendly form of <Ref id="prob:sat"/>:

<Problem id="prob:3sat" title="3-Satisfiability" label="3-SAT">
<ProblemInstance>
An instance of <Ref id="prob:sat"/> where the formula $\phi$ is in conjunctive normal form and each clause contains three literals.
</ProblemInstance>
<ProblemQuestion>
Is $\phi$ satisfiable? That is, is there an assignment of 0s and 1s to the variables such that $\phi$ evaluates to 1?
</ProblemQuestion>
</Problem>

Obviously, every <Ref id="prob:3sat"/> instance is also a <Ref id="prob:sat"/> instance. You may look at <Ref id="prob:3sat"/> and assume it is less useful than the regular <Ref id="prob:sat"/>, but that's actually not true! We mentioned above that <Ref id="prob:3sat"/> is $\NP$-complete, so there is a polynomial reduction from <Ref id="prob:sat"/><Footnote/> to <Ref id="prob:3sat"/>.

<FootnoteBody>
Or, consequently, any other problem in $\NP$.
</FootnoteBody>

That reduction is interesting in its own right, but we are not going to go through it here. Instead, for our first reduction, I'd like to introduce a problem that's given in the language of graph theory, and consequently looks more like the types of problems we've been studying. First, a few definitions:

<Definition id="def:clique" title="Clique">
A set of vertices $K\subseteq V$ in a <Ref id="def:graph" useLabel textTransform="lowercase"/> such that there is an edge between every pair of vertices in $K$.
</Definition>

<Definition id="def:kClique" title="$k$-Clique">
A <Ref id="def:clique"/> with $k$ vertices.
</Definition>

The problem we will study is:

<Problem id="prob:clique" title="Clique" label="CLIQUE">
<ProblemInstance>
A graph $G=(V,E)$ and an integer $k\in\Z_{>0}$.
</ProblemInstance>
<ProblemQuestion>
Is there a clique in $G$ of size $k$?
</ProblemQuestion>

What I'd like to do now is show you a reduction from <Ref id="prob:3sat"/> to <Ref id="prob:clique"/>. It's probably easiest to start with an example. How about this sample <Ref id="prob:3sat"/> instance:

$$ {#eq:3satInstanceToClique}
\phi = (x_1\lor x_2\lor x_3)\land(\neg x_1\lor \neg x_2\lor x_3)\land(\neg x_1\lor x_2\lor \neg x_3)
$$

Compare that to the following graph:

<Figure id="fig:cliqueInstanceFrom3sat" caption={<>The graph produced by reducing the <Ref id="prob:3sat"/> instance <Ref id="eq:3satInstanceToClique"/> to an instance of <Ref id="prob:clique"/>.</>}>
  <PrintExtra>_Interact with this content on the website_</PrintExtra>
  <CliqueReductionGraph client:load />
</Figure>

The graph in <Ref id="fig:cliqueInstanceFrom3sat"/> is built using information from our <Ref id="prob:3sat"/> instance $\phi$ in <Ref id="eq:3satInstanceToClique"/>. There is one vertex for every literal in each clause of $\phi$. In the figure, the vertex labels give first the clause being considered, then the variable in the literal represented. So the label $1-x_1$ corresponds to clause 1 variable $x_1$, the label $3-x_2$ corresponds to clause 3 variable $x_2$, and so on.

The rules for drawing edges are as follows:

- If two vertices represent the same clause, do not add an edge.
- If two vertices represent different clauses then:
  - If the two vertices represent different variables, add an edge.
  - If the two vertices represent the same variable $x_i$, add an edge if and only if the _literals_ are equivalent (i.e. do not add an edge in the case that $x_i$ appears in one clause and $\neg x_i$ appears in the other).

To check your understanding, you can go back to <Ref id="fig:cliqueInstanceFrom3sat"/> and click on some of the vertices to highlight their corresponding edges. For instance, no pair of nodes starting with the same number are connected with an edge, because that first number denotes the clause they represent. Looking across clauses, vertex $1-x_2$ has an edge to all the other cross-clause vertices, with the exception of $2-x_2$. This is because in the first clause the corresponding literal is $x_2$, while in the second clause the literal is the negation $\neg x_2$.

That's really the core of the reduction. Let's write up some very loose pseudocode to have as a reference.

<Algorithm id="algo:3sat2clique" caption="3-SAT to CLIQUE reduction">
<AlgoStep>Set $k$ to be the number of clauses in $\phi$.</AlgoStep>
<AlgoStep>Create a graph $G=(V,E)$ with three vertices per clause, each vertex representing one of the clause's literals.</AlgoStep>
<AlgoFor each="distinct vertices $v_i,v_j\in V$ (representing clauses $c_i,c_j$, literals $l_i,l_j$, and variables $x_i,x_j$)">
  <AlgoIf cond="$c_i\neq c_j$">
    <AlgoIf cond="$x_i\neq x_j$">
      <AlgoStep>Add edge $(v_i,v_j)$ to $E$.</AlgoStep>
    </AlgoIf>
    <AlgoElse>
      <AlgoStep>If $l_i$ and $l_j$ do _not_ contradict each other (i.e. it is not the case that one equals $x_i$ and the other equals $\neg x_i$), add edge $(v_i,v_j)$ to $E$.</AlgoStep>
    </AlgoElse>
  </AlgoIf>
</AlgoFor>
</Algorithm>

The claim is that this is a valid polynomial reduction from <Ref id="prob:3sat"/> to <Ref id="prob:clique"/>. As a reminder, in order to prove that we'll need to show three things:

- The transformation requires a number of steps bounded by a polynomial in the input instance's length.
- If the <Ref id="prob:3sat"/> instance is a YES instance, then the <Ref id="prob:clique"/> instance is also a YES instance.
- Conversely, if the <Ref id="prob:3sat"/> instance is a NO instance, then the <Ref id="prob:clique"/> instance is also a NO instance. Note that by <Ref id="def:contrapositive" useTitle textTransform="lowercase"/>, this is the same as saying that if the <Ref id="prob:clique"/> instance is a YES instance, then the <Ref id="prob:3sat"/> instance is a YES instance.

Let's do it.

<Theorem id="thm:3sat2Clique">
<Ref id="algo:3sat2clique"/> gives a polynomial reduction from <Ref id="prob:3sat"/> to <Ref id="prob:clique"/>.
</Theorem>

<Proof>
It is clear that the length of the input instance is directly related to the number of clauses $k$ in <Ref id="prob:3sat"/> instance $\phi$. Meanwhile, the graph created has $|V|=3k$ and $|E|$ is bounded by $k^2$. Thus the run time of <Ref id="algo:3sat2clique"/> is $\O{k^2}$.

Now let's suppose that the input is a YES instance. Then there must be some satisfying assignment of the variables, and hence in each clause there is at least one literal whose assignment evaluates to true. Take one such literal for each clause, and let $K\subseteq V$ be the set of vertices representing these literals. We claim $K$ is a $k$-clique. Clearly $|K|=k$. Also, for each distinct pair $v_i,v_j\in K$, $v_i$ and $v_j$ represent different clauses, and if they represent the same variable the literals cannot contradict each other (since they came from a satisfying assignment). So, following the rules of the construction, $(v_i,v_j)\in E$, confirming $K$ is a $k$-clique.

Now suppose that $G$ has a $k$-clique $K$. By construction, there can only be one vertex per clause in $K$ (because there are no edges between vertices representing the same clause). So there must be exactly one vertex in $K$ representing any particular clause. To satisfy $\phi$, for each vertex $v\in K$ consider the variable (call it $x_{v}$) and clause it represents. For the assignment, set $x_{v}$ to 1 if the corresponding literal is not negated in the clause, and set it to 0 otherwise. This gives us a satisfied literal in each clause, and it cannot lead to any contradictions in variable values, since contradictory vertices cannot have edges between them. Therefore such an assignment will satisfy $\phi$.
</Proof>

## Optimization is (often) hard {/* sec:optIsHard */}

With that, our surface-level tour of complexity theory is over. What was the point? Well, for one thing, it brought us this notion of polynomiality, which gives us a stronger underpinning to what we might describe as a "good" algorithm, or an "easy" problem. Among the problems we've studied so far, we know that a few of them (<Ref id="prob:shortestPath"/>, <Ref id="prob:mst"/>) fall into this "easy" camp.

On the other hand, we know there's an apparent gap between these problems and the seemingly more difficult $\NP$-complete problems. Whether that gap is real or imaginary will be up to future researchers to settle, but for now exponential algorithms are the state of the art for most of the problems we care about.

For most of the rest of the class, we will be focusing on these difficult problems, where the decision version of the problem is $\NP$-complete. These optimization problems are actually part of another class of so-called _$\NP$-hard_ problems. The definition mirrors $\NP$-completeness, in that a problem is said to be $\NP$-hard when any problem in $\NP$ has a polynomial reduction to it. The difference is that you do not need to be a member of $\NP$ to be considered $\NP$-hard<Footnote/>. So we are theoretically justified in saying that many optimization problems are hard!

<Definition id="def:npHard" title="$\NP$-Hard">
A problem for which there exists a polynomial reduction from any problem in $\NP$ to it. (In contrast to <Ref id="def:npComplete" useTitle/> problems, there is no requirement that the problem itself is a member of $\NP$.)
</Definition>

<FootnoteBody>
So $\NP$-complete is the intersection of $\NP$ and $\NP$-hard.
</FootnoteBody>

These theoretical notions also back up some rules-of-thumb to keep in mind when deciding if a solution method may scale. Polynomial steps are good. Combinatorial explosions (like we saw in our <Ref id="prob:ip"/> model for <Ref id="prob:tsp"/> in <Ref id="eq:tspIp"/>) are bad.

Looking ahead a bit, we'll spend a little more time talking about easy problems, how to recognize them, and some theory that unites them. Then it's back to the world of $\NP$-hard problems and how we can tackle them. Most of this discussion will focus on <Ref id="prob:ip"/> as a unifying framework. If you need exact solutions for these problems, either <Ref id="prob:ip"/> or methods derived from it are usually among the best choices.

Lastly, it's worth noting that even if you are faced with an $\NP$-hard problem so large that theory suggests you can never hope to prove optimality with known methods, that doesn't mean you need to give up! It's worth remembering also that most algorithmic analysis in complexity theory is a worst-case analysis. Sometimes subclasses of certain problems can be easier to solve than the entire class itself, and maybe you got lucky! Furthermore, even if exact solutions are out of reach, heuristic methods can often come to the rescue and deliver "good enough" solutions for even very large problems. We will discuss some broad classes of heuristics later in the class.
